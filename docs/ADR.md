# Architecture Decision Records

PianoGo: a single-process Next.js app with SQLite that helps beginner pianists keep a sheet-music library and see note names and piano keys for each sheet.

## 1. Next.js (TypeScript) as the single backend and frontend framework
Date: 2026-09-28
Status: Superseded by [6]
Context: The app must run as one process from one command, and the core feature is an interactive score view and piano keyboard that react when you click a note, which needs a lot of client-side code. The first skeleton (2026-09-25) was a Python app with static files, and I would have needed a separate JS frontend anyway.
Decision: Replace the Python skeleton with one Next.js App Router project in TypeScript, where `app/api/*` route handlers are the backend and React pages are the frontend, started with `npm start` (`next start -H 0.0.0.0`).
Alternatives considered: Flask + Jinja templates with plain JS was rejected because the piano view, OpenSheetMusicDisplay rendering and pdf.js overlays are all JavaScript, so I would write and maintain two languages for one small app. FastAPI + a separate React/Vite build was rejected because it means two toolchains and two manifests, which breaks the one-manifest rule.
Consequences: One language and one `package.json` for UI, API and domain logic, and libraries like `opensheetmusicdisplay` and `pdfjs-dist` can be used directly. The cost is a heavier framework (build step, server/client component rules) and native modules such as `better-sqlite3` and `@napi-rs/canvas`, which must compile inside the Assignment 2 container.

## 2. Two feature domains, Sheet library and Music processing, joined only by a sheet id
Date: 2026-09-27
Status: Decided
Context: The assignment needs two domains that could later become separate services. PianoGo naturally has two jobs: storing and organizing uploaded files, and reading those files to produce note names and piano-key mappings.
Decision: `lib/library/` owns uploads, sheet metadata, files and previews, and `lib/processing/` owns annotations, note extraction (vector PDFs and Audiveris OMR) and pitch-to-key mapping. Processing reads a sheet's file only through the library's `readSheetFile(id)`, the library never imports processing, and only the thin `app/` route handlers call both (for example, `DELETE /api/sheets/[id]` calls `deleteAnnotations` and then `deleteSheet`).
Alternatives considered: A single `lib/sheets` module that parsed notes at upload time and stored them on the sheet row was rejected because uploads would then depend on slow parsing (Audiveris takes 10-40 s per page), and the two jobs could never be separated. Splitting by layer (`lib/models`, `lib/services`) instead of by domain was rejected because both domains would be mixed in every folder, with no visible seam.
Consequences: The seam for a later split is the one function `readSheetFile(id)`, which would become an HTTP call that returns the file for a sheet id while processing gets its own database. The cost is that cross-domain work, such as deleting a sheet and its annotations, is coordinated in the route handler instead of inside one transaction.

## 3. Processing tables reference `sheets` only through `annotations.sheet_id`, with one annotation per sheet
Date: 2026-10-03
Status: Decided
Context: When I added PDF annotation I needed to store where each notehead sits on the page (page, x, y, staff spacing) so labels can be drawn over the original file, plus the user's label style. I had to decide how this data relates to the library's `sheets` table without mixing the two domains' data.
Decision: The library's `sheets` table holds no note data and the processing tables (`annotations`, `pdf_notes`) hold no title, composer or file information, so the only link is `annotations.sheet_id`, which is `UNIQUE` (a sheet has zero or one annotation). `pdf_notes` stores each PDF note's page position, pitch, measure and piano key per annotation, and the label style is a JSON `TEXT` column on `annotations`.
Alternatives considered: Putting `sheet_id` directly on every `pdf_notes` row was rejected because re-annotating would mean deleting and re-inserting notes keyed by a library id, and it would add more foreign keys into the library's table. A separate `annotation_styles` table with one column per option was rejected because style options are still changing (color, size, uppercase, octaves), and adding a column each time means a migration each time.
Consequences: Splitting processing out later only needs one foreign key (`sheet_id`) to become a plain id, and re-annotating is an upsert on `annotations` plus replacing its `pdf_notes` in one transaction. The style JSON cannot be checked by SQLite, so `parseAnnotationStyle` validates it in code, and MusicXML notes are not stored at all because OpenSheetMusicDisplay names them in the browser as it draws the score.

## 4. Unit tests on `lib/` domain logic only, with Jest, aiming for at least 70% coverage
Date: 2026-10-04
Status: Decided
Context: Coverage must be at least 70% on core business logic, and most of the code that can break in subtle ways is pure logic: input validation, pitch maths, PDF/OMR note parsing and annotation style parsing. Route handlers and React components are mostly glue.
Decision: Write Jest tests under `tests/library/` and `tests/processing/` that call `lib/` functions directly, with coverage measured only over `lib/db.ts`, `lib/library` and `lib/processing` and a 70% threshold that fails `npm test -- --coverage`. Repository tests use a real SQLite file in a temporary `DATA_DIR` per test file and fake only outside programs (pdf.js via `jest.mock`, Audiveris via a fake `spawn`), prioritizing `model.ts` validation, pitch maths in `find-notes.ts` and `read-omr.ts`, `parseAnnotationStyle`, and the repository create/update/delete and annotation status paths (`none`, `processing`, `ready`, `failed`).
Alternatives considered: Browser end-to-end tests (Playwright) of upload, annotate and play were rejected for now because they are slow, need a running server, and test Next.js wiring more than my own logic. Mocking `better-sqlite3` was rejected because a real temporary SQLite file is fast and catches real SQL mistakes. Running the real Audiveris in tests was rejected because it takes 10-40 s a page and would have to be installed wherever tests run.
Consequences: Coverage is 96% of statements and 92% of branches, with `library/preview.ts` thinnest (58%) because rendering a PDF page to PNG needs pdf.js and a real canvas, so only its cache and non-PDF paths are tested. Bugs in route handlers or UI components are not caught, and the faked pdf.js and Audiveris will not catch changes in those programs' real output.

## 5. No user accounts or login in v1
Date: 2026-09-30
Status: Decided
Context: The target is a single beginner, or a small class or studio of about 100 daily users, each practising on their own library, and the app runs locally until Assignment 2. Login would affect every table and every route.
Decision: I did not build authentication or per-user libraries. There is one shared library, and `sheets` has no `user_id`.
Alternatives considered: Email/password accounts with sessions (or NextAuth) were rejected because they add password hashing, session storage, a `users` table and ownership checks on every route. That is a third domain I would need to test and explain, while the assignment only requires two. Being able to share or sync a library across devices is real value, but it was not worth that scope now.
Consequences: Anyone who can reach the server can see, edit and delete every sheet, so a public deployment in Assignment 2 would need at least a network restriction or a simple login in front of it. Adding accounts later means a `users` table, a `user_id` on `sheets` and filtering every library query by owner, while processing would not change because it only works with sheet ids.

## 6. Split along the ADR-2 seam into a `library` service and a `processing` service, with one server-side call across it
Date: 2026-11-11
Status: Decided
Context: Assignment 2 requires exactly two services, one per domain, each with its own SQL Server database, a static UI on Azure Static Web Apps, and at least one flow that crosses the seam on the server. ADR-2 put the seam at `readSheetFile(id)`, so this is the test of whether that held. Looking at the code, it mostly did, with three places where the monolith still leaned on sharing one process and one database: `getAnnotation` joined `sheets` to tell "no annotation yet" from "no such sheet", `DELETE /api/sheets/[id]` deleted annotations and then the sheet in one handler, and uploaded files and previews were stored on the local disk under `data/`, which a Container App loses whenever it scales to zero.
Decision: Two Node.js/TypeScript services under `services/`, and the Next.js app becomes a static export in `ui/` that calls both from the browser.
- `library` owns the `sheets` table, the uploaded file bytes (moved from `data/uploads/` into a `VARBINARY(MAX)` column so they live in its database) and page previews (kept only as a regenerable local cache). Endpoints: `GET /sheets`, `POST /sheets`, `PATCH /sheets/{id}`, `DELETE /sheets/{id}`, `GET /sheets/{id}/file`, `GET /sheets/{id}/preview`, `GET /health`. It calls nothing.
- `processing` owns `annotations` and `pdf_notes`, PDF note extraction and Audiveris. Endpoints: `GET /annotations?sheetId=`, `POST /annotations`, `PATCH /annotations`, `GET /annotations/notes?sheetId=`, a new `DELETE /annotations?sheetId=`, and `GET /health`. `annotations.sheet_id` becomes a plain id with no foreign key.
- The server-side cross-seam flow is "generate annotations": `POST /annotations` in processing calls `GET {LIBRARY_URL}/sheets/{id}/file` with a timeout of `LIBRARY_TIMEOUT_S` (default 10 s) instead of calling `readSheetFile`. A 404 from library becomes a 404 "Sheet not found". A timeout, refused connection or 5xx becomes a 503 `{"error": "The library is not responding, so this sheet can't be annotated right now. Try again in a minute."}`, which the UI shows as a message, without retrying on the server. Reading existing annotations, notes and styles never calls library, so they keep working while library is down, and the library page keeps working while processing is down (the sheet view then shows the score without labels and a "note names unavailable" notice).
- `getAnnotation` no longer checks that the sheet exists. A sheet id with no annotation row returns `{"status": "none"}`, because the UI only asks about sheets it has just loaded from library.
- Deleting a sheet is done by the UI: `DELETE library/sheets/{id}` first, then a best-effort `DELETE processing/annotations?sheetId={id}`. Library stays the only source of truth for whether a sheet exists, and library never calls processing.
Alternatives considered: Having library call processing on delete was rejected because the dependency would go both ways, so neither service could be deployed, tested or reasoned about alone, and a processing outage would block deleting a sheet. Doing "generate annotations" in the UI (fetch the file from library, upload it to processing) was rejected because the assignment needs a server-side crossing and because it would push up to 20 MB through the browser twice. Having processing copy every sheet's file or metadata into its own database was rejected because it duplicates the library's data and needs a sync mechanism, while processing only needs the file once per annotation. Moving the seam (for example putting previews in processing because they also render PDFs) was rejected because previews are part of browsing the library and need only the file the library already holds.
Consequences: ADR-2 held: the only data that crosses the seam is the sheet file, now over HTTP, and only one call site in processing changes. What is lost is the database's guarantees across the seam: processing cannot know whether a `sheet_id` still exists, and if the second delete fails the annotation rows are orphaned. That is tolerated because SQL Server `IDENTITY` never reuses ids, so an orphan can never be attached to a new sheet, and handling it is part of ADR-7. Generating annotations now depends on library being up, and on Azure it may fail the first time if library is cold-starting with a paused database, which the 503 message tells the user to retry (ADR-8). Storing files in the database uses its 2 GB limit (about 100 sheets at the 20 MB maximum, far more at typical sizes of a few hundred KB). ADR-1's single Next.js process is replaced by two services plus a static UI.

## 7. Each service owns its SQL Server database and changes it only through numbered SQL migrations, run at startup, forward-only and data-preserving
Date: 2026-11-28
Status: Decided
Context: ADR-6 gives each service its own SQL Server database (`iadelino-ieu2024-library-db` and `iadelino-ieu2024-processing-db` on Azure, `pianogo_library` and `pianogo_processing` in compose), replacing the monolith's single SQLite file. In Assignment 1 the schema was created with `CREATE TABLE IF NOT EXISTS` when the app opened the file, which can create tables but cannot change one that already has rows. Once the system is deployed, the databases hold real sheets and annotations that must survive every deploy, and each service is deployed on its own, so I needed a way to change a schema that the pipeline can apply without me, that each environment (my laptop, CI, Azure) applies the same way, and that never loses data.
Decision:
- Each service keeps plain T-SQL files in its own `migrations/` folder, named `NNN_description.sql` and applied in number order. A service only ever has migrations for its own database, and its database user (`library_user`, `processing_user`) is `db_datareader`, `db_datawriter` and `db_ddladmin` in its own database only, so it can migrate its schema but cannot open the other service's database or manage users.
- A small runner (`src/migrate.ts`, about 150 lines, the same in both services) records each applied file in a `schema_migrations` table with its SHA-256 checksum. It applies each pending file in its own transaction together with its `schema_migrations` row, so a migration is either fully applied and recorded or not at all. Lines holding only `GO` split a file into batches, as `sqlcmd` does, because SQL Server compiles a whole batch before running it.
- Migrations run when the service starts, after it connects to the database and before it listens (ADR-8). A new revision therefore never serves requests against the old schema, and every environment is migrated by the same code path: `docker compose up`, the CI test databases and the Azure Container Apps.
- Migrations are forward-only. A file that has been applied is never edited: if its checksum no longer matches, the runner refuses to start, and corrections go in a new migration. There are no down migrations. Undoing a change is another forward migration, and code is rolled back by redeploying the previous image, which works as long as each migration stays compatible with the code before it.
- A change to a table that already holds data is written so existing rows keep their values. `002_add_sheet_updated_at.sql` adds `sheets.updated_at` in three steps: add it as nullable (existing rows are untouched), backfill it from `created_at` (a sheet that was never edited last changed when it was created), then make it `NOT NULL` with a `SYSUTCDATETIME()` default for new rows. Adding it as `NOT NULL` with a default in one statement would have stamped every existing sheet with the time of the deploy. The column is not in the API, so `system.yaml`, the OpenAPI files and the UI did not change.
- The data that crosses the seam is handled without a database guarantee (ADR-6): `annotations.sheet_id` has no foreign key, and an annotation whose sheet was deleted is left in place, never shown (the UI only asks about sheets it loaded from library) and never attached to a new sheet, because `IDENTITY` never reuses an id.
Alternatives considered: A migration tool or ORM (Prisma Migrate, Knex, Flyway) was rejected because each brings its own schema language or a JVM, while what I need (ordered files, one table of applied versions, a transaction each, checksums) fits in one small file I can test and explain. Writing migrations in plain T-SQL also means the files are the schema documentation. Creating the schema from code at startup (`IF NOT EXISTS` checks, as in Assignment 1) was rejected because it cannot express "change this column on rows that already exist" and leaves no record of what was applied. Running migrations as a separate CD step before deploying the image was rejected for now: it needs the database to be reachable from the GitHub runner (a firewall rule or a job inside Azure) and a credential with schema rights in GitHub, while at one replica per service (ADR-8) migrating at startup is safe. Down migrations were rejected because a down that drops a column destroys data, and they would be untested code paths. One shared database with a schema per service was rejected because ADR-6 and the assignment need each service to own its data, and a shared database would allow cross-service joins again.
Consequences: Migration 002 was applied on Azure by the CD deploy of the merge of PR #11 (`273d205`), with data in the library database. The library log shows `migration applied: 002_add_sheet_updated_at.sql`, `schema_migrations` lists 001 and 002, and a query before and after shows the same sheets with their titles, statuses and `created_at` unchanged and `updated_at` equal to `created_at`. A test in `services/library/tests/database.test.ts` repeats this against SQL Server in CI: it applies 001, inserts sheets, applies 002 and checks that every column is unchanged. If a migration fails on Azure, its transaction rolls back, the new revision never becomes healthy and CD's health check fails, while the old revision keeps serving the old schema. The fix is a new commit with a corrected file (the failed one was never recorded, so it may be edited) or a new migration. The cost of migrating at startup is that a slow migration delays the first request after a deploy, and nothing stops two replicas from migrating at once, which is why `--max-replicas` stays at 1 until migrations move into their own pipeline step (ADR-8). Because there are no down migrations, rolling back code only works if every migration is additive, so a change such as renaming or dropping a column must be split across deploys: add the new column, deploy code that uses it, and drop the old one in a later migration. Orphaned annotations accumulate slowly when the UI's second delete fails. A cleanup would need processing to ask library which ids still exist, which I have not built because the orphans are harmless and small.

## 8. Serverless on Azure: scale to zero everywhere, and cold starts handled by retrying in the service and in the UI
Date: 2026-11-26
Status: Decided
Context: The system runs in my Azure for Students subscription, where nothing may cost money while it is idle. The resources are two Container Apps (`iadelino-ieu2024-library`, `iadelino-ieu2024-processing`) in one Consumption environment, two serverless Azure SQL databases on the free offer on `iadelino-ieu2024-sql`, the storage account `iadelinoieu2024ui` with static website hosting, the managed identity `iadelino-ieu2024-github`, and the Log Analytics workspace created with the environment, all in `francecentral`. Images come from GHCR, which is free. All of these are billed per use: Container Apps per vCPU-second and GiB-second while a replica runs (with a monthly free grant), the databases per vCore-second while resumed (free up to the offer's monthly limit, and paused rather than billed past it), storage per GB and per request, and Log Analytics per GB ingested (free up to 5 GB a month). The price of this is cold starts. With `--min-replicas 0` a Container App has no replica after a few idle minutes, and a free-offer database pauses after 60 idle minutes. The first request after a quiet period has to wait for a container to start and possibly for the database to resume, which takes up to about a minute. Meanwhile SQL Server refuses connections (error 40613), and Container Apps answers the browser with `503` after about 30 s. That 503 comes from the platform and has no CORS headers, so the browser does not even see the status: `fetch` fails with a network error. Before this change, the UI treated that like any other failure, so the first visit after a quiet period showed "The library is not responding" even though nothing was wrong.
Decision: Cold starts are handled at three levels, each with a time limit.
- In each service, at startup: `connectDatabase` retries with exponential backoff (1, 2, 4, 8, then 15 s, ten attempts, about 100 s in all) and logs each failed attempt. The service then runs its migrations and only then listens on its port. So it never answers a request with a half-migrated schema, and Container Apps keeps the request waiting (or answers 503) until it is ready.
- In the UI, on every call to a service: `serviceFetch` in `ui/lib/api.ts` wraps `fetch`. It retries network errors, 502, 504 and 503s whose body is not JSON, waiting 2, 4 and then 8 s between attempts, for at most 90 s. Each attempt has its own 35 s timeout. While it waits, the top bar shows "Starting up the library service after a quiet period. This can take up to a minute…" (`ui/components/waking-notice.tsx`, in English and Spanish). If the service is still not answering after 90 s, the caller gets the failure and shows its existing error message, for example "The library is not responding…". Responses from the services themselves are never retried. They always carry CORS headers and JSON, including processing's designed 503 when library is down (ADR-6), so they reach the UI at once and are shown as they are.
- Writes are retried only when the request never reached the service: a network error or a platform 503 means Container Apps did not forward it. A write that timed out may have been applied, so it is not sent again. Reads are retried in every case.
- In CD: after deploying, the workflow polls `/health` on both services for up to 5 minutes, until each returns 200 with the new commit's SHA as `version`. This allows for a container start plus a full database resume, and makes sure the old revision is no longer the one answering.
- `--max-replicas 1` means at most one replica of each revision runs migrations at startup. Each migration runs in its own transaction with its `schema_migrations` row. During a deploy, the old revision keeps serving while the new one starts, but only the new one migrates.
Alternatives considered: Keeping one replica always on (`--min-replicas 1`) and turning off auto-pause would remove cold starts. It was rejected because it is billed around the clock, which the assignment rules out and which would use up the student credit. The free database offer does not allow changing the auto-pause delay anyway. A scheduled "keep warm" ping (for example a GitHub Actions cron calling `/health`) was rejected for the same reason: it pays to stay awake, and every ping wakes the database, which the assignment asks us to avoid. Showing the platform's error straight away and asking the user to reload was rejected, because the first visit after a quiet period would almost always look broken. Retrying inside the service only (no UI retry) is not enough on its own: while the container is still starting, the browser's request never reaches the service code, so only the client can wait for it. Retrying every failure in the UI, including the services' own 5xx answers, was rejected because it would hide designed failures (processing reporting that library is down) behind a long wait.
Consequences: After a quiet period, the first visit shows the "starting up" notice for up to about a minute and then loads normally, without a reload. Later requests are fast until the system is idle again. The browser cannot tell a container that is starting from a service that is down, because both are a network error without CORS headers. So when a service is really down (for example `docker compose stop library`, or a crash loop on Azure), the UI shows the starting-up notice for 90 s before the error. I accepted this because on Azure the starting-up case is the common one. If a POST's response is lost after the service applied it, the user can see an error for something that worked, but it is never applied twice. With migrations at startup, a slow migration delays the first request after a deploy, and a failing one stops the new revision from starting while the old one keeps serving (recovery in ADR-7). At 100x traffic (thousands of users a day) the system would rarely be idle, so cold starts would matter less than capacity. I would raise `--max-replicas` and add an HTTP scaling rule. Migrations would then move out of startup into a separate pipeline step (or take a `sp_getapplock` lock), because several replicas could otherwise start at once. I would also keep `--min-replicas 1` on library during the day, move the databases off the free offer to a provisioned or higher serverless tier with a longer auto-pause delay, and move sheet files out of the database into Blob Storage.
